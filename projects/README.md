# Case-study directory system

Each case study lives in `projects/<slug>/`:

```
projects/
  <slug>/
    project.json
    FEATURE_AND_MODULE_INVENTORY.md  # or another Markdown file named by project.json.inventory
    assets/
      cover.webp                     # or cover.svg
      screen-01.webp
      flow.svg
      walkthrough.mp4
    index.html                       # generated by npm run build
```

`project.json` describes the project, not fabricated metrics: `slug`, `title`, `eyebrow`, `subtitle`, `summary`, `overview`, `category`, `repository`, `inventory`, `cover`, `stack`, `highlights`, `workflows` (`main` and optional `core`), and `media`. The same source builds a featured thumbnail card on the homepage and a complete case-study page at `projects/<slug>/index.html`.

The Markdown module parser recognizes headings `## Main — Identity`, `## Core storefront — Catalog` and `## Unverified / excluded`, plus module headings `### 01. Module title`, `**Functionality:**`, `**Data/contracts:**`, `**Implementation status:**`, and `**Source files:**`. For projects with a different structure, adapt the manifest and parser to the actual Markdown rather than guessing. The frontend displays functionality and clickable source evidence, while preserving the implemented/unverified distinctions.

Only add media you own or can publish. Media isn't magically generated from a Markdown inventory. The gallery explicitly identifies architecture illustrations; replace or expand it with genuine screenshots/videos later. The project page has a gallery viewer that supports `screenshot`, `diagram`, and `video`.

**Workflow:** drop the next project directory in, add the Markdown and assets, write an accurate manifest, run `npm run build && npm run check`, review the generated case study, and merge. Do not edit generated HTML by hand.


## New: tabular feature inventories (APAEA)
The generator now recognizes a second input format: a Markdown table headed `| # | Module | Short details | Source status |`. Every numbered row becomes a source-backed record with the **exact** supplied status, including `Present`, `Present (limited)`, `Present; live status unverified` and `Not found`.

For this format set `renderer: "research"` (research-publication case-story layout), and optional `moduleGroups` arrays in `project.json` listing the exact feature numbers per domain. The parser validates that every source-present row belongs to exactly one group, while `Not found` rows stay in a separate evidence section. The research renderer adds an independent editorial workflow and full gallery, but uses the shared responsive CSS and accessible modal controls.

For GitLab projects, `repository` may be a `https://gitlab.com/<owner>/<repo>` URL, with `commit` naming the pinned SHA. The case study links to the pinned repository tree, never invented per-feature file paths. Do not treat unprovided documents named in the inventory (such as `APAEA_AI_CONTEXT.md`) as if their content had been reviewed.


## Priority Fix: short existing/proposed feature briefs

For short briefs headed `# Project Modules and Features - Priority Fix`, the `renderer: "tenant"` parser reads `## Existing App Features` and `## Requested Modules (Proposed Scope)` separately. The former powers the current-capabilities cards and a conceptual repair journey. The latter renders a visually distinct **PROPOSED · NOT BUILT** roadmap, never an implemented badge or delivery metric.

A `repository` property is **not required** for a source-free feature brief; do not invent GitHub links, tech stacks, exact engineering ownership or live metrics. Project assets live in `projects/priority-fix/assets/`, and media entries in its manifest feed the existing gallery viewer. The current SVG diagrams are expressly conceptual; add genuine screenshots and videos only when supplied and approved.
