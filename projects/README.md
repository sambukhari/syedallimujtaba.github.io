# Case-study directory system

Each case study lives in `projects/<slug>/`:

```
projects/
  <slug>/
    project.json
    FEATURE_AND_MODULE_INVENTORY.md  # or another Markdown file named by project.json.inventory
    assets/
      cover.webp                     # or cover.svg
      screen-01.webp
      flow.svg
      walkthrough.mp4
    index.html                       # generated by npm run build
```

`project.json` describes the project, not fabricated metrics: `slug`, `title`, `eyebrow`, `subtitle`, `summary`, `overview`, `category`, `repository`, `inventory`, `cover`, `stack`, `highlights`, `workflows` (`main` and optional `core`), and `media`. The same source builds a featured thumbnail card on the homepage and a complete case-study page at `projects/<slug>/index.html`.

The Markdown module parser recognizes headings `## Main — Identity`, `## Core storefront — Catalog` and `## Unverified / excluded`, plus module headings `### 01. Module title`, `**Functionality:**`, `**Data/contracts:**`, `**Implementation status:**`, and `**Source files:**`. For projects with a different structure, adapt the manifest and parser to the actual Markdown rather than guessing. The frontend displays functionality and clickable source evidence, while preserving the implemented/unverified distinctions.

Only add media you own or can publish. Media isn't magically generated from a Markdown inventory. The gallery explicitly identifies architecture illustrations; replace or expand it with genuine screenshots/videos later. The project page has a gallery viewer that supports `screenshot`, `diagram`, and `video`.

**Workflow:** drop the next project directory in, add the Markdown and assets, write an accurate manifest, run `npm run build && npm run check`, review the generated case study, and merge. Do not edit generated HTML by hand.
